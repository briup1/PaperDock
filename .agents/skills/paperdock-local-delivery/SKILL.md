# PaperDock 本地交付

仅适用于当前 PaperDock 仓库。正文和脚本留在项目，不安装全局、不上传 OpenViking。相对于本 Skill 目录，仓库根为 `../../..`，执行脚本为 `../../../app/local_delivery.py`。

## 授权与停止

用户明确调用本 Skill，即授权本次选定改动的 Git 提交、本机安装和下述限定清理；不再逐步询问。泛泛讨论、只读检查、加载 Skill 本身不等于执行授权。

- 不推送、不发布、不生成分享 ZIP、不改安全设置或开机启动。
- 不混入其他人的改动；选定文件内部有不属于本次的改动时，先停止说明，不能整文件提交。
- 不强杀或退出其他项目/其他人的实例。只退出当轮核对过、以 `--old-pid` 指定的唯一 PaperDock 实例；多实例时停止。
- 不迁移、复制、清空或回退便签数据库。涉及数据格式变动/不明兼容性时停止，另行确认。
- 测试不全或失败不能填“通过”；说明缺口，取得用户接受后才可批准交接。脚本中的测试说明是事实声明，不是自动判定器。

## 两部分的交接

### 第一部分：开发与验证结束前

需求提出到开发验证由相邻 `../paperdock-change/SKILL.md` 负责；指纹、实际结果和下述交接由执行者自动维护，不让用户手动传参数。以下是两部分共用的脚本交接约定，不在本 Skill 重做需求开发流程。

1. 读项目 `AGENTS.md`、核对 `git status` 和本次 diff，确定逐文件提交范围；不使用 `git add .`。部分暂存的选定文件须先解决，不自动改写用户暂存区。
2. **测试开始前**调用 `fingerprint --paths <逐个文件>`，保留输出的 `fingerprint`。脚本指纹包括 HEAD、拟提交源码树和选定文件；与构建相关的未选改动会被拒绝。可在此时把必要的源码改动加入范围，不准借此夹带无关内容。
3. 执行本轮必要自动化验证与开发者实际操作验证，记录真实命令、证据位置、结果和未验项。测试后代码变了须补受影响验证；只改文档时也重新取指纹并做对应文档检查。
4. 调用 `approve`，传同一组文件、测试前指纹、自动化结果、开发者结果、未验项及明确的 `--data-compatible` 声明。输出交接保存在 Git 忽略的 `.work/local-delivery/ready.json`。指纹不符会拒绝。

```bash
python3 /绝对项目路径/app/local_delivery.py fingerprint --paths app/Sources/Example.swift
# 随后实际执行必要测试，不要直接复制占位结果。
python3 /绝对项目路径/app/local_delivery.py approve \
  --fingerprint <测试前输出> \
  --automated '<真实命令、结果和证据路径>' \
  --developer '<实际操作、结果和来源；缺项须先取得接受>' \
  --limitations '<未验或已接受风险；确实没有才填无>' \
  --data-compatible --paths app/Sources/Example.swift
```

示例文件和 `/绝对项目路径` 均为占位，调用前替换为真实绝对路径及逐个实际文件。已有交接无需重新执行第一部分；没有交接不能把当前指纹倒填成“测试前指纹”，须补最小受影响验证。

### 第二部分：用户调用交付

1. 读交接并核对测试记录，不重跑整套开发流程。用当前 `ps` 命令行核对旧进程的绝对二进制、PID、`--data-dir`，不得沿用 README 中历史 PID。无 `--data-dir` 时，须明确核实其默认数据位置；目录不明确只问这一处。
2. 固定安装位置为当前用户的 `Applications/PaperDock.app`。首次安装也必须明确沿用现有数据目录，不能静默切到空库。现有实例在隔离验收目录时，沿用该目录需要用户当轮明确选择，不能把任意测试库当日常库。
3. 以绝对脚本路径执行；`--old-pid` 仅在存在已确认旧实例时传入：

```bash
python3 /绝对项目路径/app/local_delivery.py deliver \
  -m 'feat: 本次改动说明' \
  --data-dir /已核实的现有数据目录 --old-pid <已确认PID>
```

执行顺序：再核对指纹 → 从拟提交源码树独立构建 → 只提交选定文件 → 校验提交树 → 写入提交号并本地 ad-hoc 签名 → 请求旧版正常退出并等待 → 同卷替换安装 → 用原数据目录启动 → 确认同一 PID 已完成 AppKit 启动及安装版本 → 清理。无代码差异但交接仍有效时沿用 HEAD，可重试提交成功但安装失败的交付，须对当前 HEAD 重新建立交接，不重复造空提交。

正常启动不等于完整功能验收；签名仅本机完整性签名，不是 Developer ID/公证。关于面板显示版本与 Git 短提交号。

## 清理边界与失败处理

- 不产生 ZIP。只有安装并启动核对成功后，删除仓库 `dist` **直接子文件**中严格匹配 `PaperDock-数字.数字.数字-trial-arm64-macOS26.zip` 及相应 `.zip.sha256` 的非软链文件。
- 不递归清理 `dist`，不删历史解压目录、`artifacts`、数据、测试证据、其他 ZIP。需要首次清理历史解压应用时单独列范围获准，不假借本 Skill 扩大删除。
- 构建临时目录自动回收。安装替换期间临时保留一份旧 `.app`；新版启动核对成功后删除。启动失败保留旧 `.app` 路径，不自动降级用户数据、不杀进程。
- Git 提交成功后发生签名、退出、安装或启动失败：如实报“代码已提交，本机更新未完成”及恢复位置；不撤销提交、不伪造全部成功、不删除旧 ZIP。
- 旧版保存失败/拒绝退出/等待超时：停止，不强杀、不替换。新版失败后人工排查并正常退出，再重建交接重试。

最后报告：Git 提交号、本机安装路径/运行 PID/版本、沿用的数据目录、删除的具体包、测试未验项和失败恢复位置（如有）。最近结果位于 `.work/local-delivery/last-result.json`；不以历史结果冒充本次成功。

## 维护与自检

修改本流程后执行 `python3 /绝对项目路径/app/test_local_delivery.py -v`；测试使用临时 Git 仓库和安装目录，不触碰用户应用。该测试模拟 GUI 启动，不能替代真实 AppKit helper 编译与隔离实例启动验证。脚本不安装依赖，使用已有 Python 3.9+、Swift/CLT 和系统命令。

Pi 从项目 `.agents/skills` 发现此 Skill；新增或修改后执行 `/reload`，随后用 `/skill:paperdock-local-delivery` 强制调用，也可以说“执行 PaperDock 本地交付”。其他宿主是否扫描此目录须按宿主实际能力核对，不承诺所有宿主自动发现。
