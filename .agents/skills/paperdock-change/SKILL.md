# PaperDock 改动开发

本 Skill 负责两部分流程的第一部分，不是新的流程引擎。只在 PaperDock 项目使用；相对本目录 `../../..` 是仓库根。所有命令先解析成真实绝对路径，不能执行文中占位值。只用当前宿主已确认可用的能力，不默认多 Agent、监听服务、定时任务或额外依赖。

## 入口、授权与分流

```text
用户描述改动 → 核对现状与已有批准
  → 确认会改变结果的业务选择 → 开发
  → 按影响验证与聚焦 Review → 必要时让用户体验明确的候选版
  → 自动生成测试交接 → 停止，等待另行调用本地交付
```

- 单纯问原理、建议或现状：只答，不进入开发。Bug/回归转现有 `wl-investigate`，先复现再修；纯 Git 操作不走本流程。
- 用户明确要求开发即可在已明确范围内执行；只批准需求但未批准具体方案，不等于委托 Agent 自动采用所有技术决策。已批准做法和边界复用，不再例行询问；确有新选择时给一个推荐、影响及最小问题。
- 读取当前项目 `AGENTS.md`、README 当前入口、涉及的 `app/README.md` 章节及相应需求文档；查 Git 状态/差异以保留已有改动。已有未提交文件不自动算本轮范围，尤其不能把别人的源码混入候选构建。
- 命中源码结构/影响分析且存在 `.codegraph` 时按项目规则先查图；没有则定点读直接依赖，不扫全库。
- 默认只写本次项目文件、构建产物与独占测试数据。不提交、推送、正式安装、覆盖运行应用、删除历史包、迁移真实数据或改全局 Skill。

## 1. 确认：一份预期贯穿后续

新需求加载现有 `wl-req-confirm`，用例需要生成时加载 `wl-qa-test-planner`；执行这些能力时按当前清单真实位置读取，不复制其模板。已有对应需求则原位维护，不新建另一份同义正文。

从用户这次操作写清“当前怎样 → 哪处变化 → 什么不变”，具体数据、操作和预期只在既有用例正文维护。简单改动材料保持简短，不能因为简单省略必要的业务确认、安全条件或用例审查。已确认业务不重复提问；有适用的正式基线审查要求仍需执行，不把自检叫独立审查。

例如“标题条再窄一点”：宽度还是高度不明确时，只问这个会改变结果的选择；若已明确降低高度，不再询问如何改代码。保留折展、标题可读、拖后恢复、锁定禁止折展等直接相关预期，不顺带重做整个窗口。

## 2. 开发：复用已有能力，不另造平台

- 编码前加载 `at-standards`；需要明确实施方案时用 `wl-design-doc`；已有批准方案开始实施时按需加载 `wl-ticket-run`。跨阶段复杂任务才使用 `wl-auto-delivery`，不因有这些 Skill 就每轮通读整个流水线。
- 实现只改本轮目标和直接必要依赖，非平凡逻辑留最小回归检查。没有源码改动的文档/Skill 任务无需构建应用。
- 发现影响数据格式、保存退出、输入法候选或现有钉住规则时，按真实影响扩大验证；涉及真实数据迁移、不可逆变化或超范围操作先停下说明。
- `app/run.sh` 不保证源码修改后重建。所有候选使用显式新构建，绝不能把旧 `app/build` 当新版。

## 3. 验证：按改动选，不全跑也不漏关键链

先核对本轮逐个文件及 diff，保证自动交接脚本可用。测试**开始前**调用 `app/local_delivery.py fingerprint --paths <逐个文件>`，把输出保存到本轮独占证据目录。不要把指纹工作交给用户。若构建输入存在不属于本轮的未提交修改，停止说明，不扩大选定范围来绕过拒绝，也不能拿混杂源码测试后称为本次候选。

当前构建和测试命令以项目指南为准，按实际修改选择：

| 本次影响 | 必要验证及边界 |
|---|---|
| 仅文档或 Skill | 内容/本地链接/加载与场景推演，不启动便签、不跑无关 Swift 测试 |
| 字号、留白、标题条尺寸 | 构建＋受影响的展开/折叠/锁定等状态实际视觉核对；编译不能代替视觉 |
| 折展、拖动、锁定、删除行为 | 相关规则/持久化测试＋同一操作链实际体验；不凭历史 CompactTests 结果认定本轮通过 |
| 保存、退出、布局或存储格式 | 对应规则、失败保护、正常退出重开及必要旧格式兼容；真实库迁移仍须独立授权 |

可复用 `app/test.sh`、`app/test-pin-delete.sh`、`app/test-compact-icon.sh` 或已构建程序的相关 `--test` 套件。每个 runner 使用各自尚不存在的绝对构建/证据目录；它们自行构建，不重复在同一路径预构建。测试生成的全新目录和日志保留，不清空旧失败。

需要执行测试/验收时加载 `at-test`；需要具体实现 Review 时加载 `at-review`，只审本轮 diff 和直接影响。若缺少独立审查能力或要求的证据，记录阻断，不伪造独立结果、不临时降低门槛。

测试选择和结果写在该需求既有执行记录中：引用用例、运行目录、真实命令/退出码、实际操作、结果与未验项；不再复制一套预期。程序自驱、内容缓存图、截图、真人反馈须区分。失败修复后补受影响验证并保留原失败，重复失败时按项目故障处理规则停止无效重跑。

## 4. 候选版本：用户只负责需要真人的体验

- 只有应用源码/资源有变化且确实需要体验时才准备候选。使用项目内本轮唯一目录，例如 `artifacts/developer/<本轮名称>/candidate/build/PaperDock.app`；构建、数据、证据都隔离，不覆盖日常应用或旧候选。
- 可以复用本轮测试实际使用的候选二进制，前提是能核对其对应源码、测试后未变化，且不是只有测试替身的程序。否则显式重新构建，补必要核对。
- 默认空隔离库；场景确需数据时使用现有 `--seed-fixture`，只写新空库。不得复制日常便签、复用另一进程数据目录或导入未经授权真实资料。
- 只构建不会运行；给用户一个带**绝对二进制、明确 `--data-dir` 和独占 `--evidence-dir`** 的完整启动命令。不单独发 `.app` 双击链接，以免无参数打开默认日常库；不用 `open -a`。
- 开发者能完成的操作先做，用户仅补真实手感/输入法/跨应用等缺口。只在获准时启动候选，按 PID 和绝对路径记录归属。自有自动探针结束后正常退出并核对；交给用户持续体验的实例明确交接，不悄悄关闭。不能为测新版退出用户当前实例。

给用户的体验说明仅包含：本次变化、候选入口、对应源码指纹、要体验的几个用例引用/简短操作、未验项。用户说“通过”须对应到该候选和具体范围，不能算其他历史功能全部通过。

## 5. 自动交接：不给用户维护内部参数

1. 完成记录和 Review 修复后，重新核对全部本轮文件。指纹不符时，判断变化影响并补相应验证；先取新指纹再验证，不能验证完倒填“测试前指纹”。文档新增/修改也影响拟提交树，内容稳定后补对应检查即可，不机械重跑全部功能测试。
2. 需要用户体验但尚未反馈时，状态为“待体验”，保留本轮指纹/候选/结果，不写 `ready.json`。已有旧交接可能仍在，不能当本轮交接使用。
3. 有失败、未执行、审查阻断时，状态为“未完成”，不批准交接；只有用户明确接受相应缺口并同步受影响范围后，才能按调整后的基线继续。体验不适用（例如纯文档）写明依据，不伪造操作。
4. 确认数据格式未变且兼容性无未决问题后，读取相邻 `../paperdock-local-delivery/SKILL.md` 的“第一部分：开发与验证结束前”，按其唯一脚本交接约定调用已有 `approve`，传入测试前指纹、实际自动化/开发者结果、证据路径、未验项及逐个文件。命令参数不在此复制维护。

`approve` 仅记录事实声明，不会执行测试、验证声明真实性或安装应用；真实性由执行者核对。若数据格式变化，不因测试通过就勾选 `--data-compatible`，先处理兼容与迁移授权。

交接通过后输出简短结果：“改了什么；验证结果/未验项；候选入口（如有）；已生成交接还是待体验”。不要自动调用 `deliver`。第二部分入口为相邻 `../paperdock-local-delivery/SKILL.md`，用户另行明确调用时才执行 Git 提交、安装和限定清理。

## 恢复与验证边界

继续上次任务先读该需求的执行记录、当前 Git 差异和实际候选路径；指纹/源码不符不能继承旧通过。已有事实足够就停止加载，不新增流程数据库、队列、候选目录清理器或全局同步。

本 Skill 是 Agent 操作指引：按影响选择测试、聚焦 Review、生成交接由 Agent 调用已有能力完成，不是后台自动运行。Skill 加载/文案检查只能证明可发现和关键约束存在；没有实际新功能运行证据，不宣称“需求到测试全链已验”。
