# 开发流程规范

范围：开发、交接与资料维护；状态：当前；依据：项目 Skill、需求归档及授权约束。

## 需求与资料归宿

[docs/requirements](../../requirements/README.md) 是唯一归宿，不迁往 `docs/changes` 或在 Harness 复制。已有需求原位维护；新需求核对同义需求和空号后建 `{编号-主题}/`，向相关能力传入真实目录。

| 资料 | 唯一正文 / 例外 |
|---|---|
| 需求、批准范围、执行阶段 | `requirement.wl-req-confirm.md` |
| 具体数据、操作、预期 | `test-cases.wl-qa-test-planner.md`；0006 沿用 `test-cases.md` |
| 技术方案 | `design.wl-design-doc.html` 或既有局部方案，不为齐全补造批准 |
| 实施、Review、执行结果 | 既有执行记录/审查报告，引用原始证据 |
| 长期规则与当前实现 | `docs/harness/rules/`、`wiki/`；重要规则/取舍变化在本需求留 `规范变更.md`，普通链接修正无需另记 |
| 本机入口与候选路径 | 忽略的 `.harness-local/testing.md`，不写凭据、登录态或真实便签 |

需求/用例 HTML 用同目录 `render-docs.py` 生成，不直接改；方案 HTML 是独立正文。产物/本机证据沿 [.gitignore](../../../.gitignore) 忽略，不改既有受控 `assets/` 历史。新证据确认合成/脱敏及保存范围，不提交真实库、运行日志或登录态。

## 从需求到交付

```text
提出变化 → 核对源码、既有需求与 Git 差异 → 确认新旧结果和批准范围
  → 用例/必要方案及审查 → 获准实现 → 聚焦验证与 Review
  → 必要时隔离候选供真人体验 → 交接结果与未验项 → 停止
  → 用户另行明确调用本地交付 → 核对交接后提交/安装
```

| 任务 / 阶段 | 入口与动作 |
|---|---|
| 询问、建议、文档维护 | 只答或只改获准文档，不启动业务开发 |
| 新需求 | [paperdock-change](../../../.agents/skills/paperdock-change/SKILL.md) → `wl-req-confirm`；已有批准复用，不重复问 |
| 方案与实现 | 按需用方案/实施能力；编码前读 `at-standards`，保留已有改动，不扩范围 |
| Bug / 回归 | `wl-investigate`：先复现再修复 |
| 验证与 Review | 按[测试规范](测试规范.md)选直接影响，加载对应 Skill；不能把自检称为独立审查 |
| 候选与交接 | 执行者按改动 Skill 维护源码指纹、候选和结果；源码变更后补受影响验证 |
| 本地交付 | [paperdock-local-delivery](../../../.agents/skills/paperdock-local-delivery/SKILL.md) 负责收尾；普通开发不运行 `deliver` |

能力按宿主真实位置加载，缺能力/证据就记缺口。指纹与候选操作见改动 Skill；未选构建输入被拒绝时停止，不夹带无关改动。

## 确认与操作边界

需求批准不等于委托所有技术选择；新增影响结果、不可逆或超范围选择才补确认。批准、实现、验证、体验、安装与发布分别表达；编译成功不等于功能通过。

| 操作 / 情况 | 授权与停止条件 |
|---|---|
| 默认开发 | 不提交、推送、安装、关闭用户实例、清理历史包或发布；打包发送、外部写入及权限调整须当轮授权 |
| 明确调用本地交付 | 授权选定文件提交、本机安装及 Skill 限定清理，不含推送/发布；只读取 Skill 不构成调用 |
| 候选运行 | 仅获准时启动，使用独占数据/证据路径，不双击或用 `open -a`，不为测新版退出用户实例 |
| 数据冲突 / 保存失败 | 不杀进程、不清空坏库、不擅自复制/迁移/回退真实数据；退出用户实例须核对归属及授权 |
| GUI 争焦点、权限提示、兼容性未决 | 停止相应操作；不能因测试通过就声明未知格式的数据兼容 |
| 继续历史任务 | 重核源码、路径、实例和证据；旧 PID、旧 ready、手工快照及历史授权不自动续用 |

## 完成与资料回写

交付负责人说明“改了什么、实际检查、直接缺口和下一步”；原失败保留，重测引用新轮次，不覆盖旧结果或拿历史截图补位。

| 交接情况 | 记录与动作 |
|---|---|
| 待真人体验 | 留绝对二进制、独占数据/证据路径、源码指纹及少量用例引用；状态待体验，不写 ready |
| 有失败、未执行或审查阻断 | 不写通过/完成；用户明确接受缺口并调整相应基线后，才继续交接 |
| 证据与条件满足 | 按交付 Skill 生成 `approve`；脚本只记录声明，不验证真实性，更不等于安装 |
| 用户反馈通过 | 只覆盖该候选与对应操作，不外推全部功能；体验不适用时注明依据 |

首次实现或职责/接口/状态/长期规则变化后，交付负责人回读根入口及受影响正文并补缺；无稳定事实变化则说明无需同步。原位维护，不要求重跑 setup，不另建手册/台账。

## 来源与未覆盖

- 流程与命令由上述两个项目 Skill 维护；验证方式见[测试规范](测试规范.md)，本文不复制参数。
- 批准与历史结果见[需求索引](../../requirements/README.md)，不能证明当前版本已通过或获授权。
- 公开分发、Developer ID/公证和跨系统支持不在本流程内，须另行确认。
